## Decision precedence and interpretation

For Core refactoring, D-01–D-12 in the orchestration prompt supersede only incompatible package/DTO/helper placement conventions and the former prohibition on behavior corrections. This does not change OpenAPI, private-service, persistence, or product contracts; behavior corrections need reproduced evidence and regression tests. D-01–D-12 apply to Core only and do not authorize B-01–B-16 or Questions/Email refactors.

| Category | Recorded rule |
| --- | --- |
| Architectural principles | Inward dependencies; domain decisions independent of transport and infrastructure; application coordination; explicit data ownership; replaceable external mechanisms with preserved behavioral contracts. Domain behavior may use cohesive behavior-bearing objects or data with pure transition functions. Features are not assumed to be DDD bounded contexts. |
| AJA conventions | Feature packages; separate `domain/` and `application/`; `InputPort`, `OutputPort`, `UseCase` suffixes; `Command`/`Query` inputs and semantic results; only explicitly published immutable contracts cross feature boundaries; no mixed `Support`/`Helper`/`Utils`/`Base`/`Generic`; selected verification mechanisms. These are project choices, not universal hexagonal rules. |
| Migration constraints | One Core process and Gradle project; existing JDBC/SQL; no schema/migration change; preserve OpenAPI/private contracts, cookie, status/error precedence, authorization, snapshots, idempotency, lock/transaction protocols, and outbox delivery. No JPA, gateway, BFF, or other-service refactor. These constraints do not define all future systems. |

## Cross-feature write/transaction protocols

| Operation / owner | Application coordinator | Atomic write boundary and invariant | Required evidence |
| --- | --- | --- | --- |
| Email/token confirmation affecting pending enrollment (`identity` + `academic`) | Identity confirmation capability | Existing Core SQL transaction updates identity/token and only eligible pending enrollments atomically; preserve lock order, revalidation, and rollback. No identity adapter general authority over academic writes. | Real PostgreSQL rollback/concurrency test; method and HTTP auth/error precedence tests. |
| Creation of subjects and modules, module order and visit recording (`curriculum`) | Curriculum create use cases coordinate authorization, typed receipt replay and atomic persistence; order and visit use cases coordinate their named store operations. | Existing advisory auth gate, then class rows, sorted teacher rows, subject and module locks where applicable. Creation and the associated receipt commit together. Order requires the complete current module/revision set. Visit records merge only the caller's verified publication IDs with the caller's previous visit. | `CurriculumIntegrationTests` lock/race and receipt tests; `CurriculumStoreContract` shares order/visit outcomes with the in-memory substitute. |
| Announcement notification (`announcements` + `outbox`) | Announcement application operation | Business row, recipient-scoped event/outbox row, idempotency record commit/rollback together; `notify=false` emits none. | PostgreSQL commit/rollback plus RabbitMQ confirm/retry/outbox contract evidence. |
| Identity registration/confirmation/reset events (`identity` + `outbox`) | Identity operation | Identity/token/audit and outbox record atomic; secrets never included in responses/logs/events beyond current versioned contract. | PostgreSQL atomicity and outbox serialization/crypto tests. |
| Material publish/update/reorder (`materials` + `curriculum`) | Materials application operation coordinates material/file changes and the existing `modules.revision` / `subject_publications` updates through `MaterialWriteOutputPort`. `PublishMaterialsUseCase` also owns the receipt lookup/save transaction with `EncodedIdempotencyStoreOutputPort`. | Same transaction; preserve module revision compare-and-set and file staged owner/purpose/module/expiry checks, subject publication insertion, actor/session/teacher authorization. | Assessment create/update/publish (`assessment` + `materials` + `curriculum`) | Assessment application operation coordinates authoring and existing file/publication updates; outbox is not involved unless a currently documented event exists. | Same transaction for assessment/questions and `files` status/metadata changes plus `subject_publications`; preserve snapshot content/hash/revision, file ownership/purpose, teacher/class authorization, and assessment revision.
