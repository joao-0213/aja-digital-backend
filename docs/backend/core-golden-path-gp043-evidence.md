## Boundaries

- Assessment owns the authoring state, snapshots and revision reset. The existing PostgreSQL write protocol acquires the global authorization advisory lock, locks module scopes in sorted order, then locks the assessment and idempotency key. The same transaction keeps assessment state, snapshot rows, audit and receipt consistent, including the existing deletion of pending attempts and their matching start receipts on confirmed edits.
- Core identity remains the source of the session and actor. The authoring write contracts hold the existing redacted actor reference. PostgreSQL evaluates the persisted current role when building assessment read filters. The retained-actor regression changes the persisted role while leaving the session active and verifies denial after assignment authorization changes.
- Dashboard consumes only the assessment input ports and their published query/projection contracts. Its summary contains assessment state and question count with the existing role-conditional assignment field. Attempts and submissions keep their existing ports.
- Core reads module, subject, class, teacher and enrollment relationships for visibility and locks. It reads users and sessions for current authorization, reads attempts and submissions for edit eligibility and pending counts, and retains the existing image-copy and publication side effects. It calls Questions only through the authenticated private snapshot client. A literal SQL comparison found the same 45 statements/fragments, four write transaction annotations, one read-only transaction, six `FOR UPDATE` clauses and one global advisory lock. Pagination offsets bind as `Long` so supported high page values avoid integer wraparound.
- Assessment owns its application failures and maps them to the existing HTTP error bodies. Its bank snapshot provider moved into the assessment application boundary with a defensive query and result. Legacy Forum keeps its existing call to this capability for GP-04.7.
